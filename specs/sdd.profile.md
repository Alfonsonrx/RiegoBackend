## Project rules
1. **Ownership.** Every record a user creates (sensor, schedule, notification) is visible and
   changeable only by that user, and a foreign record answers "not found", never "forbidden". *Why:*
   every table already carries the owner's id; a missing filter leaks one grower's greenhouse to
   another, and "forbidden" confirms the record exists.
2. **Authenticated by default.** Every endpoint requires a valid bearer token, except register, login,
   the database health check and reading ingestion, which a sensor authenticates with its own ingest key
   (spec 102 D4, amends the original rule). *Why:* the token is the only identity the API has; a
   microcontroller must not hold its owner's password.
3. **Secrets stay in settings.** Passwords and ingest keys are stored only as one-way hashes, tokens
   are signed with a key read from settings, and no response, log or spec carries a hash, a key or a
   password (an ingest key is shown once, at creation or regeneration). *Why:* the brief's data is
   small, the credentials are not.
4. **Brief traceability.** Every FR of a 1xx spec names the brief's RF id it serves (`RF1`…`RF7`) in its
   paragraph, or says it serves none. *Why:* the prototype is judged against the brief; a requirement
   with no RF is scope creep, an RF with no FR is a gap.
5. **Versioned schema** *(Alembic set up in 002 T07; start-up `create_all` removed in 002 T08)*. A schema change ships as an
   Alembic migration, not as a change to table creation at start-up. *Why:* a deployed database
   keeps its history of readings; recreating tables would drop it.
